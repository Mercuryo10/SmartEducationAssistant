# 需求规格说明书

> 配套文档：`00-项目总览.md`（技术规格基线）· `09-开发计划与验收.md`（构建顺序与验收）。
> 本文档只描述**需求**（做什么），不描述实现细节；实现方案见 `02~06` 各设计文档。

## 1. 角色定义

| 角色 | 说明 |
|------|------|
| 大学生（Student） | 主要用户（面向**想学大模型/Agent 的大学生**）：提问、传作业、看错题分析、做练习题、收复习提醒 |
| 讲师（Teacher，简化） | 可选角色：维护知识库 / 参考答案，演示时可与大学生角色合并 |

> 校招项目简化：系统不区分真实权限，登录仅作演示与数据隔离；默认提供演示账号 `demo / demo123`。

## 2. 功能需求（按 Agent）

### 2.1 智能答疑 Agent（QA）

**用户故事**：

- US-QA-1：作为学生，我可以**输入文字问题**，系统基于知识库 RAG 返回带**溯源出处**的回答，以便我信任答案。验收：回答中能引用知识库文档来源；无相关知识时明确说明「知识库中未找到」。
- US-QA-2：作为学生，我可以**上传问题图片**（拍下的题目照片），系统先用 OCR 提取文字再回答。验收：图片中的题目文字被正确识别并进入问答流程。
- US-QA-3：作为学生，我可以**语音提问**，系统转写为文字后回答。验收：音频文件被转写，且进入同一问答链路。
- US-QA-4：作为学生，我可以**连续多轮对话**，系统记住上下文。验收：在同一个 conversation_id 下，追问能结合前文（如「那第二问呢？」）。
- US-QA-5：作为学生，我可以查看**历史对话记录**。验收：`GET /api/v1/conversations/{id}/messages` 能取回历史。

**边界与规则**：

- 多模态优先顺序：语音 → 转文字；图片 → OCR 提取；两者与文本可同时出现。
- 回答必须**流式输出**（SSE），逐 token 展示。
- 知识库内容默认使用 `scripts/demo_data/` 下的样例（如「注意力机制」「RAG 原理」「Agent 工作流」等大模型/Agent 领域文档）。

### 2.2 作业批改 Agent（Grading）

**用户故事**：

- US-GR-1：作为学生，我可以**上传作业照片**（一张或多张），系统识别并批改。验收：图片经 OCR 输出可读文本。
- US-GR-2：作为学生，我可以为**客观题**（选择题/填空题/判断题）获得自动判分。验收：对照答案给出「对/错」与总得分。
- US-GR-3：作为学生，我可以为**主观题**获得 AI 参考评分与改进建议。验收：每题给出评分(0-100)、一句话评语、改进建议。
- US-GR-4：作为学生，我可以看到**逐题批改明细**（题号、题目、学生答案、标准答案、得分、评语）。验收：结果 JSON 结构完整可展示。

**边界与规则**：

- 答案来源：演示模式使用题目自带的参考答案（demo 数据）；接口支持传入 `answer_key` 文本。
- OCR 识别失败时返回明确错误提示，不阻塞其他题。
- 客观题自动判分不消耗 LLM；主观题评分调用 Qwen（在批改结果中标注「AI 参考评分」）。

### 2.3 错题分析 Agent（Mistake）

**用户故事**：

- US-MS-1：作为学生，我可以**录入/导入错题**（文本或图片），系统自动关联**知识点**。验收：错题记录含知识点标签。
- US-MS-2：作为学生，我可以**查看错题列表**并按知识点筛选。验收：`GET /api/v1/mistakes?knowledge_point_id=xx` 可过滤。
- US-MS-3：作为学生，我可以**获得薄弱知识点归纳**（哪些知识点错得最多）。验收：返回按错误次数排序的知识点 TopN。
- US-MS-4：作为学生，我可以对某道错题**请求个性化讲解**（生成解法 + 该知识点讲解 + 常见错误模式）。验收：`POST /api/v1/mistakes/{mistake_id}/analyze` 返回结构化解讲。

**边界与规则**：

- 知识点体系：内置一份精简知识点清单（如大模型/Agent 领域：注意力机制 / Transformer 架构 / 提示工程 / 检索增强生成 RAG / Agent 与函数调用 / 微调与 LoRA / 幻觉与缓解 等），存 `knowledge_points` 表，支持脚本初始化。
- 薄弱点归纳可用**简单统计 + LLM 文案总结**两种方式；统计必须真实（不虚构数据）。

### 2.4 练习生成 Agent（Exercise）

**用户故事**：

- US-EX-1：作为教师/学生，我可以**指定知识点、难度、题型、数量**生成练习题。验收：返回参数匹配的题目列表。
- US-EX-2：系统生成题目时**难度可控**（简单/中等/困难）。验收：同知识点不同难度生成题目，复杂度明显不同。
- US-EX-3：同一组参数可**重复生成**且内容不同（避免一模一样）。验收：两次调用结果不完全相同。
- US-EX-4：生成的题目带**参考答案与解析**。验收：每题含 `answer` 与 `explanation`。

**边界与规则**：

- 实现采用「**参数化模板 + LLM 填充/微调**」：预置题目模板（含可替换数字/变量），LLM 按难度调整参数并生成解析，保证题目可解、答案正确。
- 模板覆盖至少 3 种题型（选择 / 填空 / 解答）与至少 3 个知识点（见 demo 数据）。

### 2.5 学习推送 Agent（Push）

**用户故事**：

- US-PU-1：作为学生，我可以**创建一条复习提醒**（内容 + 触发时间），系统到时推送。验收：到达时间后 `push_logs` 新增一条成功记录。
- US-PU-2：系统按**遗忘曲线**规则（如 1 / 2 / 4 / 7 天间隔）自动生成复习计划。验收：为某学生知识点生成 4 个复习时间点。
- US-PU-3：作为学生，我可以**查看推送历史**。验收：`GET /api/v1/push/logs` 返回记录列表。
- US-PU-4：推送渠道支持**可扩展**（演示默认写日志/控制台，标注可接企业微信/邮件/短信）。验收：渠道层是接口，新增渠道无需改业务代码。

**边界与规则**：

- 定时调度用 APScheduler 后台任务；服务重启后任务从数据库 `push_tasks` 恢复。
- 「触达」在演示环境为 mock（写日志），真实渠道属于可扩展点。

## 3. 非功能需求

| 类别 | 要求 |
|------|------|
| 运行环境 | **双模式**：开发期笔记本（Windows 11，Python 3.11）；生产期实验室 Ubuntu（RTX 4090） |
| 业务数据库 | MySQL 8.0（开发期本机实例，生产期连接已部署实例） |
| 性能 | 常规文本问答首 token < 5s；OCR 单张图片 < 10s（CPU）；语音转写（≤30s 音频）< 15s |
| 内存 | 常驻内存目标 < 4GB（PaddleOCR / faster-whisper 使用惰性加载 + 进程内单例） |
| 并发 | 支持 3~5 个并发请求即可（校招演示场景） |
| 可观测性 | 统一 `logging` 输出；关键链路（OCR/检索/LLM 调用）记录耗时日志 |
| 错误处理 | 外部依赖（DeepSeek / 千问 / 本地模型 / 中间件）失败时返回结构化错误，不崩溃 |
| **可扩展性 / 可移植性** | **后端接口化 + 配置切换**：向量库（FAISS↔Milvus）、缓存（内存↔Redis）、LLM/Embedding（云端↔本地）同一套代码切换；存储仓储化、工具层可插拔、推送渠道可扩展 |
| 安全（简化） | API Key 只在 `.env`，不进代码库；上传文件限类型与大小（≤10MB） |

## 4. 数据需求（对应 `03-数据库设计.md`）

系统需持久化：用户、对话消息、知识库文档、作业提交与批改结果、错题、知识点、练习题、推送任务与日志（业务数据落 MySQL）。向量数据（知识库分块）存向量库后端（开发 FAISS / 生产 Milvus），元数据关联 MySQL 的 `knowledge_docs`。

## 5. 需求优先级

- **P0（必须）**：2.1 智能答疑、2.2 作业批改、2.3 错题分析
- **P1（应有）**：2.4 练习生成、2.5 学习推送
- **P2（可延后）**：严格鉴权、多教师、真实推送渠道、批量导入

> 建议按 P0 → P1 顺序实现，与 `09-开发计划与验收.md` 的分阶段构建保持一致。
