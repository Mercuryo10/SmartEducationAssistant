## 第三关：答辩/面试题（本项目面试讲解主线）

### Q1：项目为什么用「多 Agent」而不是一个巨大的 prompt？
> 单一 prompt 无法同时做好答疑/批改/错题/出题/推送五类专业任务；拆成专业 Agent + 统一编排，职责单一、可独立迭代。

### Q2：为什么用「接口 + 工厂」抽象存储/缓存/LLM？
> 开发（FAISS+内存+云端）和生产（Milvus+Redis+本地）后端不同；接口化 + 配置切换，同一套代码只改 `.env` 就能迁移——体现可移植性。（这是简历亮点）

### Q3：为什么数据库访问要走仓储层？
> 数据访问收口、业务不碰 SQL、换库只改 data 层；配合 ORM 模型，代码有类型提示、不易出错。

### Q4：项目怎么保证「每个阶段都能跑」？
> 分 8 个阶段，每阶段结尾有验收清单（`docs/09`），通过了才进入下一阶段；避免一次性铺开全部代码。

### Q5（进阶）：`create_all` 为什么是幂等的？外键级联怎么处理的？
> 检查表存在则跳过；本项目软删除不做、物理删除，级联关系靠外键约束。

## 第四关：挑战题（做完才算真的会）

1. **找 bug**：打开 `app/storage/vector_store.py` 的 `FaissVectorStore.search`，假设传一个长度不是 1024 的向量，会发生什么？怎么让它报错更友好？（提示：先看 `dim`）
2. **加后端**：参照 `MemoryCache`，给项目新增一个 `FileCache`（用 JSON 文件存缓存），实现 `Cache` 接口，并在 `get_cache()` 加一个 `VECTOR_BACKEND`… 不，`CACHE_BACKEND=file` 分支。业务层需要改动吗？（答案：不用）
3. **读流程**：不看代码，凭记忆画出 `init_db.py` 的执行流程图。
4. **实践验证**：把 `.env` 的 `APP_ENV` 改成 `prod`，重启服务，观察 health 返回的 `llm` 字段变化（因为 `check_llm_config` 只看 `llm_provider` 与 key，`APP_ENV` 本身不影响——发现没变？说明你已经理解配置项各自的作用域）。
