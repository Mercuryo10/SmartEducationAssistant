# 07 · 抽象层：接口与工厂（本项目最大的加分项）

> 目标：看懂 `cache.py`、`vector_store.py`、`llm.py` 里「接口 + 工厂」的写法，理解它为什么是简历和答辩上的亮点。
> 对照文件：`app/storage/cache.py`、`app/storage/vector_store.py`、`app/services/llm.py`。

---

## 1. 从问题开始：开发的痛

项目要**开发/生产两套后端**：

| 东西 | 开发（笔记本） | 生产（Ubuntu+4090） |
|------|----------------|---------------------|
| 向量库 | FAISS | Milvus |
| 缓存 | 内存 TTL | Redis |
| LLM | DeepSeek 云 API | 本地 Qwen |

如果业务代码直接 `import faiss`、`import redis`，那么换环境 = 改一堆代码 = 噩梦。

**想要的效果**：业务层只写一遍，运行环境变了只改 `.env`，代码零改动。

## 2. 解法：接口（interface / Protocol）

先定义一个「大家都认可的约定」——不管背后是 FAISS 还是 Milvus，都要会这几招：

```python
class VectorStore(Protocol):
    def add(self, chunks): ...
    def search(self, vector, top_k=5): ...
    def delete_by_doc(self, doc_id): ...
    def count(self): ...
```

- `Protocol` 在 Python 里就表示"接口"：**只声明方法长什么样，不写实现**。
- 业务代码只认这个接口，**不关心**背后的实现是 FAISS 还是 Milvus。
- 所以业务层永远写 `store.search(...)`，从不写 `faiss.xxx(...)`。

> 类比：插座。电器（业务）只认"两孔插座"这个接口，你给它接电网还是发电机（实现）都行。

## 3. 解法：工厂（factory）

「接口」定义了约定，「工厂」负责按配置造出正确的实现：

```python
def get_cache() -> Cache:
    if settings.cache_backend == "redis":
        return RedisCache()        # 生产：Redis
    return MemoryCache()           # 开发：内存

def get_vector_store() -> VectorStore:
    if settings.vector_backend == "milvus":
        return MilvusVectorStore()
    return FaissVectorStore()
```

**调用方（业务代码）**：

```python
from app.storage.cache import get_cache
cache = get_cache()          # 到底返回内存还是 Redis？看 settings，业务不关心
```

- 只要后端实现满足接口（都有 `get/set/delete/clear`），换后端就是 `get_cache()` 里多一行分支。
- **这就是"配置切换后端，代码零改动"的实现原理。**

## 4. 用真实的 `cache.py` 拆解一遍

```
app/storage/cache.py
├── class Cache(Protocol)      ← 接口：4 个方法签名
├── class MemoryCache          ← 实现①：cachetools.TTLCache，进程内存
├── class RedisCache           ← 实现②：import redis（惰性，装了才用）
└── def get_cache()            ← 工厂：按 settings.cache_backend 返回
```

**注意这两个细节**：

### 细节①：惰性导入（lazy import）

```python
class RedisCache:
    def __init__(self):
        import redis        # ← 用到才 import
```

- 开发环境不装 redis 也能跑——因为只有选了 redis 后端，这个 `import redis` 才会执行。
- 同样的写法在 `vector_store.py`（faiss 在 `__init__` 里 import）、`llm.py` 都有体现。
- 这就是为什么 `requirements.txt` 里 `pymilvus`/`paddleocr` 等重依赖现在不装也能启动。

### 细节②：协议 vs 实现分离

- 业务层**只 import** `get_cache`（工厂）和 `Cache`（接口）。
- 项目规范：**业务代码禁止 `import redis` / `import faiss` / `import pymilvus`**（docs/08 §3）。
- 违规怎么查？`grep -rn "import faiss\|import redis" app --exclude="storage"`——之前自查过，无违规。

## 5. `llm.py` 也是同一个套路

```python
def get_chat_llm(temperature=0.3) -> ChatOpenAI:
    if settings.llm_provider == "local":
        return ChatOpenAI(model=settings.local_llm_model, base_url=settings.local_llm_base_url, api_key="ollama")
    return ChatOpenAI(model=settings.deepseek_model, base_url=settings.deepseek_base_url, api_key=settings.deepseek_api_key)
```

- DeepSeek 和本地 Ollama 都走 **OpenAI 兼容端点**（同一个 `ChatOpenAI` 类，只是 base_url/model 不同）。
- 一个工厂切换云 / 本地模型。后面 RAG、答疑 Agent 都从 `get_chat_llm()` 拿模型。

## 6. 这套设计为什么是"加分项"？

面试时你可以讲：**「存储、缓存、LLM 全部接口化 + 配置切换，同一套代码从笔记本平滑迁移到生产环境，迁移时只改 .env，代码零改动。」**

- 它证明你懂「面向接口编程」，而不是写死具体实现。
- 它证明你考虑过「可移植性 / 环境差异」这类真实工程问题。
- 答辩演示：切换 `VECTOR_BACKEND` / `CACHE_BACKEND`，服务行为不变——直观且有力。
