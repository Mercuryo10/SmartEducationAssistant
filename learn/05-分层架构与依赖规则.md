# 05 · 分层架构与依赖规则

> 目标：看懂「为什么代码要分层」，以及「依赖方向为什么必须是 api → services → storage」。
> 这是企业级开发最核心、也是面试最常被问到的概念之一。

---

## 1. 三层架构图

```
        ┌─────────────┐
        │   api 路由层  │  ← 管"HTTP 接口"：收请求、校验、返回 JSON
        └──────┬──────┘
               │ 调用
        ┌──────▼──────┐
        │ services 服务层│  ← 管"业务逻辑"：调谁、怎么算、用什么数据
        └──────┬──────┘
               │ 调用
        ┌──────▼──────┐
        │ storage 数据层│  ← 管"数据"：MySQL / 缓存 / 向量库 / 仓储
        └─────────────┘
```

**依赖方向是单向的**：上层可以调用下层，下层绝不能调用上层。

| 模块 | 可以调用 | 禁止调用 |
|------|----------|----------|
| `api/*` | services、schemas | 直接操作 storage、直接调 tools |
| `services/*` | storage、core | api、agents |
| `storage/*` | core、models | api、services 等任何上层 |
| `core/*` | （什么都不依赖） | — |

## 2. 为什么一定要这样分层？

用「健康检查」讲一遍（阶段一里真实的例子）：

- `app/api/health.py`：只管「这是 GET /health 接口」→ 调用服务。
- `app/services/health_service.py`：管「怎么探测数据库、怎么判断配置」。
- `app/storage/db.py`：管「怎么连数据库」。

问题来了：**为什么 `api/health.py` 不能自己直接连数据库？**

- 如果 100 个接口都自己连数据库，数据库换连接方式，100 处都要改。
- 接口层混入了业务细节，代码变"面条"，没法测试、没法复用。
- 各层职责清晰，才好分工、才好写单元测试。

> 这就是分层的好处：**每一层只关心一件事，改动的影响被限制在那一层。**

## 3. 阶段一里的一个真实修正（重要）

早期版本里 `api/health.py` 是直接 `from app.storage.db import engine` 探测数据库的——这违反了「api 禁止直接操作 storage」。

修正方式是**新增 `services/health_service.py`**，把数据库探测逻辑下沉到 services 层，api 只调用服务：

```python
# app/api/health.py（改后）
from app.services.health_service import check_database, check_llm_config

def health_check():
    db_status = check_database()      # ← 业务逻辑在 service 里，不在 api 里
    ...
```

**这个修正本身就是很好的学习材料**：找一个违反分层的地方 → 想明白该归哪层 → 动手搬过去。

## 4. 为什么依赖方向不能反过来？

如果 `storage` 里 import 了 `api`：

- 改接口 → 可能影响数据层 → 本来互不相干的东西耦合在一起。
- import 形成环（api 依赖 storage，storage 又依赖 api）→ 项目没法启动，思维上也没法理解。

**「单向依赖」让代码的调用关系像水流一样清晰，这就是可维护性。**

## 5. 动手练习

1. 用「查找引用」验证分层：在 `app/api/health.py` 里点 `check_database`，看它定义在哪个文件？那个文件又 import 了什么？（答案：在 services 层，import 的是 storage 的 engine——服务层调数据层，正确方向。）
2. 在 `app/storage/db.py` 里试着 `from app.api.health import router`（故意反向 import），跑 `python -c "import app.storage.db"`，观察报错/循环依赖现象——**看完立刻删掉，别留下**。
3. 打开 `docs/08 §3` 的依赖表，用「哪些文件 import 了谁」验证一遍 `grep` 结果。
