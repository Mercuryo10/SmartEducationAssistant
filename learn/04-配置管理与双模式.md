# 04 · 配置管理与双模式

> 目标：看懂 `app/core/config.py` 为什么是「全项目的源头」，以及 dev/prod 双模式怎么切换。

---

## 1. 为什么配置要集中管理？

试想：如果数据库地址、API Key 分散写死在十几个文件里——

- 换数据库？几十处都要改，漏一处就炸。
- 密钥写死在代码里 → 提交进 git → 泄露。
- 开发/生产环境不同 → 没法切换。

**企业级做法**：所有配置收口到一个文件（`config.py`），从 `.env` 读取，业务代码只写 `settings.xxx`。

```python
# 错误示范（写死在业务代码里）
DATABASE_URL = "mysql://user:pass@localhost/db"   # ❌ 别这样

# 正确做法（读配置）
from app.core.config import settings
engine_url = settings.database_url                 # ✅ 改环境只改 .env
```

## 2. 读 `app/core/config.py`（三个重点）

```python
class Settings(BaseSettings):
    app_name: str = "EduMentor"      # ① 每个字段 = 一个配置项
    database_url: str = "mysql+pymysql://..."
    vector_backend: str = "faiss"
    cache_backend: str = "memory"
    ...
    model_config = SettingsConfigDict(env_file=".env", ...)  # ② 从 .env 读
settings = Settings()                # ③ 单例：全项目共用一份
```

### 重点①：字段 = 配置项
`database_url: str = "..."` 表示配置项 `DATABASE_URL`，默认值是双引号里的字符串。
`.env` 里的 `DATABASE_URL=...` 会**覆盖**默认值。

> `pydantic-settings` 的魔法：字段 `database_url` 自动匹配 `.env` 里的大写 `DATABASE_URL`（大小写不敏感）。

### 重点②：`env_file=".env"`
启动时读取项目根目录的 `.env` 文件，把里面的键值对覆盖到 Settings 字段上。

### 重点③：`settings = Settings()` 单例
模块加载时就创建一次。业务代码 `from app.core.config import settings` 拿到的**永远是同一个对象**。这就是「配置全局唯一」。

## 3. 双模式是怎么实现的？

项目支持 dev（开发）和 prod（生产），核心是这些开关：

| 开关（.env） | 开发值 | 生产值 | 影响 |
|--------------|--------|--------|------|
| `LLM_PROVIDER` | `deepseek` | `local` | 用云 API 还是本地模型 |
| `EMBEDDING_PROVIDER` | `qwen` | `local` | 用千问 API 还是本地嵌入 |
| `VECTOR_BACKEND` | `faiss` | `milvus` | 用本地 FAISS 还是 Milvus |
| `CACHE_BACKEND` | `memory` | `redis` | 用内存缓存还是 Redis |
| `APP_ENV` | `dev` | `prod` | 运行模式标记（影响日志/echo 等） |

**代码层面：`get_vector_store()` 等工厂函数读 `settings.vector_backend`，返回不同实现——这就是"接口 + 工厂 + 配置"三个东西合起来的效果**，下一节展开。

> 本项目还有个细节：`db.py` 里 `echo=(settings.app_env == "dev")` —— 只有 dev 才打印 SQL 日志，生产不打印（省性能、不泄露）。

## 4. 检索常量为什么也放配置？

`vector_dim=1024`、`retrieve_top_k=5`、`chunk_size=500` 这些不是随便写的，是**项目基线**（docs/00 §8）。
放配置里是为了：改一个常量，所有引用处统一生效，而不是去代码里到处找。
