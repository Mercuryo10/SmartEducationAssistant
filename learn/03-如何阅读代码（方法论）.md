# 03 · 如何阅读代码（方法论）★最重要的一节

> 目标：学会一套「拿到任何陌生代码都能读进去」的方法。企业级代码动辄上万行，**没有人逐行读**——高手读的是「地图 + 数据流」。
> 学完立刻用这个方法，把你自己的 `scripts/init_db.py` 完整读一遍。

---

## 一、先纠正三个误区

| 误区 | 真相 |
|------|------|
| 「我要从第一行读到最后一行」 | 代码不是小说。90% 的行是细节，先看结构，需要时才下钻 |
| 「函数都要读懂才能继续」 | 函数先看**名字和签名**猜到职责，细节用到再读 |
| 「读代码就是看代码」 | 读代码 = 读结构 + 追数据流 + 动手改验证，三件事 |

## 二、读代码的三层地图

把读代码分成三个层面，永远先做上层：

```
第 1 层 结构层：这个项目/文件由哪些部分组成？各自的职责？
   ↓
第 2 层 数据流层：一个请求/一个数据，从哪来、经过谁、到哪去？
   ↓
第 3 层 细节层：某个具体函数怎么实现（只在需要时进入）
```

## 三、具体步骤（一套可复用的流程）

### 步骤 1：先看目录，猜职责（10 分钟）

- 看文件夹名：`api`（对外接口）、`services`（业务）、`storage`（数据）、`core`（基础设施）……
- 看文件名的动词/名词：`health_service.py` → 健康的服务？→ 猜"健康检查的业务逻辑"。
- **先猜再验证**，猜错也没关系，验证本身就在加深理解。

### 步骤 2：找到「入口」，顺着走

Python 项目常见入口：

- `main.py` 里的 `app = FastAPI()`（Web 服务入口）
- 脚本里的 `if __name__ == "__main__": main()`

从入口出发，跟着 import 跳转，画出一棵「调用树」。

### 步骤 3：追一个数据流（最关键的功夫）

选一个「具体的东西」追：一条 HTTP 请求、一条数据库记录、一个配置值。

对它不停问三个问题：

```
① 谁调用我？     → 它的上游是谁（找 import / 找引用）
② 我调用谁？     → 它的下游是谁
③ 数据长什么样？ → 进出的是什么结构（dict？ORM 对象？Pydantic 模型？）
```

### 步骤 4：用 IDE 工具，而不是用眼睛

| 操作 | 快捷键（VS Code） | 用途 |
|------|------------------|------|
| 跳转定义 | `F12` 或 Ctrl+点击 | 点函数名跳到它实现 |
| 查找引用 | `Shift+F12` | 看谁在调用它，理解它被期望做什么 |
| 全局搜索 | `Ctrl+Shift+F` | 搜类名/函数名，找所有出现位置 |
| 面包屑/大纲 | 顶部 | 看函数列表，快速定位 |

**「查找引用」是读代码最重要的技能**：一个函数的作用，从「谁在用它、怎么用」能看出一大半。

### 步骤 5：动手改 + 跑，验证理解

改一行 → 跑 → 看变化。比如把 `app/main.py` 里日志那行改一下，重启看输出。
**能预测改动的结果，才算真的读懂了。**

## 四、完整演示：读一遍 `scripts/init_db.py`

用上面的流程，把阶段一最有代表性的一段代码读穿。

### 第 1 层 结构

```
scripts/init_db.py
├── 开头：sys.path.insert(...)         ← 让脚本能找到 app 包（下面讲）
├── import 区                          ← 它要用哪些模块
├── 常量 SEED_KNOWLEDGE_POINTS/DEMO_USER ← 内置数据
├── 3 个函数：seed_* ×2 + main
└── 底部：if __name__ == "__main__": main()  ← 入口
```

### 第 2 层 数据流

```
python scripts/init_db.py
  ↓ 执行 __main__ 块
main()
  ↓ 调用
Base.metadata.create_all(engine)   → 连 MySQL，把 models.py 里 12 张表建出来
  ↓ 然后
with SessionLocal() as session:    → 开一个数据库会话
  ├── seed_knowledge_points(session)
  │     ↓ 对每个内置知识点：查重（name 已存在？）→ 不存在就 KnowledgeRepository 写入
  └── seed_demo_user(session)
        ↓ 查 demo 用户名存在？→ 不存在就 UserRepository 写入（密码先 hash 过）
  ↓
session.commit()                   → 提交，数据真正落库
```

### 第 3 层 细节（挑 3 个一开始会懵的点）

**① `sys.path.insert(0, str(Path(__file__).resolve().parents[1]))` 是什么？**

- 你要 `from app.storage.repositories import ...`，Python 得知道 `app` 包在哪。
- 脚本文件在 `scripts/` 里，`parents[1]` = 项目根目录。
- 这行把「项目根目录」加进模块搜索路径 → 之后就能 `import app...` 了。
- **为什么不直接 cd 到根目录？** 因为 `python scripts/init_db.py` 运行时，Python 默认只把脚本所在目录加入路径，不包含根目录。

**② `create_all(bind=engine)` 是幂等的？**

- `Base.metadata.create_all()` 会检查每张表**是否存在**，存在就跳过。
- 所以跑第二次不会重复建表、不会报错——这就是「幂等」。
- 同理，知识点/账号写入前都有 `get_by_xxx` 查重。

**③ `session.flush()` vs `session.commit()` 的区别？**

- `flush`：把变更发给数据库但**不提交**（事务内可见，能拿到自增主键）。
- `commit`：真正落库。repo 的 `create` 方法里用 flush 拿到 `obj.id`，最后 main 里统一 commit。

## 五、在企业级代码里你还会见到哪些"套路"（混个脸熟）

| 套路 | 本项目的例子 | 为什么存在 |
|------|-------------|-----------|
| 分层 | `api → services → storage` | 每层只管一件事，好改好测 |
| 配置集中 | `app/core/config.py` | 换环境只改 `.env` |
| 接口 + 工厂 | `get_cache()` / `get_vector_store()` | 开发/生产切后端，代码不动 |
| 仓储模式 | `repositories/` | 数据访问收口，业务不碰 SQL |
| 异常统一 | `app/core/exceptions.py` | 所有错误同一套 JSON 结构 |
| 契约先行 | `app/schemas/` | 先定接口长什么样，再写实现 |

这些每个都会在后续章节展开。**现在先记住"它们存在、为了什么"即可。**

## 六、练习：用这套方法读 `init_db.py`

1. 打开 `scripts/init_db.py`，按「结构→数据流→细节」走一遍。
2. 用 `F12` 跳进 `KnowledgeRepository`、`UserRepository`，再跳进 `BaseRepository`，看 `create` 做了什么。
3. 用 `Shift+F12` 查 `hash_password` 被谁调用。
4. 改一行：把 `DEMO_USER` 的昵称改掉 → 删掉 users 表 → 重跑 init_db → 看 MySQL 里昵称变了没。（这验证你对「幂等写入」的理解）
